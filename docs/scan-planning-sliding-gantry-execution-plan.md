# 扫描规划：滑轨机架、扫描范围与扫描方向执行方案

> 状态：已实施，待验收  
> 日期：2026-07-23  
> 适用范围：WT32 控制台原型的 Scout 定位、协议详情、扫描会话与后续确认流程。

## 1. 目的与结论

本方案处理当前“起始位置 / 结束位置”“扫描方向”“进出床”混用的问题。

WT32 的设备前提是：**患者与检查床固定，机架沿滑轨移动完成采集。** 因此：

- 用户可配置的扫描方向统一为 **头向足** 或 **足向头**。
- 每个采集序列（包括 Scout 定位像）都必须有自己的扫描范围和扫描方向；改变扫描方向时不得交换范围边界值。
- 每个采集序列的机架滑轨起点、终点和运动方向由系统在原型流程中推导；不作为普通用户参数。
- 本项目是产品与 UI 验证原型。机架运动映射仅用于模拟展示，必须经设备坐标系和流程要求确认后才可作为演示规则使用；不代表真实设备控制。

本方案采用“范围、解剖采集方向、机架运动”分离的模型，承接讨论文档中的核心建议，同时按 WT32 的滑轨机架结构修正“床运动”表述。

## 2. 现状与问题

### 2.1 已观察到的实现

1. Scout 定位页维护 `startPos`、`endPos`，并提供“交换起始/结束位置”按钮。
2. 定位完成后，这两个值仅写入浏览器 `localStorage`；后端扫描会话只更新 Topogram 的 `scan_length = abs(end - start)`，没有保存定位像本身的范围边界、方向或机架运动信息。
3. 后续确认页绘制裁剪框时会对保存值执行 `min(start, end)` 和 `max(start, end)`，并把该范围作为后续诊断规划的初始显示。
4. 协议详情把 `IN / OUT` 作为“扫描方向”编辑；协议层还存在独立的 `table_direction` 字段。

### 2.2 造成的风险

- “交换起止位置”会改变原始存储顺序，但不会改变后续显示的范围，UI 行为和数据语义不一致。
- `IN / OUT` 当前既可能被理解为扫描方向，也可能被理解为机架滑轨运动方向；`table_direction` 又形成重复概念。
- 定位像本身及后续诊断序列的实际范围边界都不随扫描会话持久化；刷新、切换会话或多个后续诊断序列共享一个 Scout 时无法可靠追溯。
- 将范围仅折算为 Topogram 的扫描长度，不能表达“定位像本身的采集运动”以及“一个 Scout 规划多个诊断序列，且每个序列范围不同”的情形。

## 3. 目标术语与职责

| 概念 | 面向对象 | 说明 | 是否由普通用户配置 |
| --- | --- | --- | --- |
| 患者摆位 | 检查 / 扫描会话 | `HFS`、`FFS`、`HFP`、`FFP` | 是 |
| 扫描范围 | 每个扫描会话采集序列 | 当前序列覆盖的两个空间边界和长度；Topogram 与诊断扫描各自独立 | 是，在对应规划步骤确认 |
| 扫描方向 | 每个扫描会话采集序列 | `HEAD_TO_FOOT`（头向足）或 `FOOT_TO_HEAD`（足向头） | 是 |
| 机架滑轨运动 | 每个采集序列的执行模拟 / 工程信息 | 由该序列的范围、扫描方向、摆位和已确认坐标约定推导 | 否 |

禁止继续把“进床 / 出床”作为用户可见的扫描方向。现有 `IN / OUT` 与 `table_direction` 均不再承担“扫描方向”含义。

## 4. 目标数据模型

### 4.1 协议模板

协议模板为每个采集序列（包括 Topogram）保留可复用的默认值：

- `patient_position`
- 每个采集序列（包括 Topogram）的 `scan_direction`
- `scan_length` 等已有协议参数

模板**不保存**本次患者 Scout 产生的绝对位置边界。固定坐标属于单次检查，不得由会话编辑反向修改模板。

### 4.2 扫描会话

在每个扫描会话采集序列（Topogram / Helical / Axial；后续按需要扩展）上增加一份独立规划数据：

```ts
type ScanPlanning = {
  scan_session_series_id: number;
  source_topogram_series_id?: number | null;
  range_min_position_mm: number;
  range_max_position_mm: number;
  scan_direction: "HEAD_TO_FOOT" | "FOOT_TO_HEAD";
};
```

规则：

- `range_min_position_mm <= range_max_position_mm`，服务端强制校验。
- `scan_length_mm = range_max_position_mm - range_min_position_mm` 为派生值；在允许的兼容期内与原有 `scan_length` 同步。
- Topogram 的 `source_topogram_series_id` 为 `null`：其范围描述定位像本身的采集覆盖和机架运动。
- 诊断序列的 `source_topogram_series_id` 指向其实际依据的已完成 Topogram；同一 Scout 可以为不同诊断序列保存各自独立的 `ScanPlanning`。
- 规划数据属于扫描会话副本，生命周期与会话一致。

### 4.3 机架滑轨运动（派生，不作为普通配置）

```ts
type SimulatedGantryMotion = {
  gantry_start_position_mm: number;
  gantry_end_position_mm: number;
  rail_motion_direction: "POSITIVE" | "NEGATIVE";
};
```

该对象由**当前采集序列的** `ScanPlanning + patient_position + 已确认的机架坐标系映射` 计算。Topogram 和每个诊断序列均须各自得到一份运动结果。默认不写入协议模板；如需在模拟执行记录中展示，可保存为执行时快照并标记为模拟信息。

## 5. 交互方案

### 5.1 Scout 定位页（现图 1）

- 将“起始位置 / 结束位置”改为“范围下界 / 范围上界（mm）”，或采用已确认坐标系对应的等价中性文案；该范围首先属于当前 Topogram 定位像。
- 删除“交换起始 / 结束位置”功能；数值录入或采集后始终规范化为 `min / max`。
- 增加“扫描方向”控件，显示“头向足 / 足向头”。切换方向时，两个范围边界和长度保持不变。
- 定位完成后，把范围与方向写入当前 **Topogram 会话序列** 的规划，并生成该定位像的模拟机架滑轨运动；不再只更新 Topogram 的扫描长度。
- Topogram 完成后，后续诊断规划以该 Topogram 的范围为可视化依据；技师为每个目标诊断序列确认独立的范围与方向，并建立 `source_topogram_series_id` 关联。

### 5.2 协议详情页（现图 2）

- “扫描方向”下拉选项改为“头向足 / 足向头”，底层值改为 `HEAD_TO_FOOT / FOOT_TO_HEAD`。
- 不在普通协议页展示或编辑 `IN / OUT`、`table_direction`、机架滑轨运动方向。
- 机架运动如确有工程展示需要，单独标注“模拟机架滑轨运动（需确认）”，只读显示。

### 5.3 后续确认与执行页

- Topogram 确认/执行页显示该定位像的范围下界、范围上界、长度、扫描方向及其派生的模拟机架运动。
- 诊断确认页显示当前诊断序列的范围下界、范围上界、长度、扫描方向及关联的 Topogram；Scout 裁剪框只从规范化后的范围边界恢复，不依赖历史 start/end 的先后顺序。
- 每个执行页只可展示当前序列派生的模拟机架运动；不得暗示真实机架控制或安全确认。

## 6. 后端与数据迁移

### 6.1 实施步骤

1. 为扫描会话的每个采集序列增加 `ScanPlanning` 持久化模型、Pydantic schema 与 API。
2. 为模板和会话序列的扫描方向定义新枚举，替换 `IN / OUT` 的用户语义。
3. 更新会话创建的克隆逻辑：模板方向复制到会话，患者本次范围不从模板复制。
4. 更新 Scout 保存逻辑，使其明确写入 Topogram 自身的会话规划；Topogram 完成后再为各目标诊断序列创建或更新独立规划。
5. 兼容期内保留原 `scan_length`，由范围差值同步更新；确认所有调用方完成迁移后再评估收敛。
6. 将 `table_direction` 从用户流程移除，保留为历史字段或另行迁移为内部的机架滑轨派生信息。

### 6.2 迁移原则

- 既有 `IN / OUT` 没有可可靠推断的解剖方向；迁移将其重置为原型界面的默认值 `HEAD_TO_FOOT`，而非将其解释为真实机架或临床采集方向。
- 既有会话补建方向记录，但不补造患者本次扫描范围；范围仍须在会话流程中确认。
- 迁移必须保留协议模板与扫描会话的副本边界：更新会话不得修改模板。

## 8. 验证与验收

### 8.1 自动化测试

- 范围输入任意顺序后，持久化值始终满足 `min <= max`，长度正确。
- 切换“头向足 / 足向头”时，范围边界和长度不变化。
- Topogram 自身可保存范围、方向及派生的模拟机架运动，并在刷新后正确恢复。
- 同一个 Scout 下两个诊断序列可保存不同范围，互不覆盖，且均正确关联该 Scout。
- 新建会话从模板复制默认方向，但不会复制患者绝对范围。
- 更新扫描会话规划不会修改协议模板。
- 旧 `IN / OUT` 数据不会被误转换为新的解剖方向。
- 在已确认的演示坐标映射下，四种摆位与两种扫描方向均得到预期的模拟机架起止方向。

### 8.2 人工流程验证

1. 使用本地测试账户创建检查并选择含 Topogram 与诊断序列的协议。
2. 在 Scout 页面采集两个范围边界，确认 Topogram 页面显示其范围、长度、方向和模拟机架运动。
3. 完成 Topogram 后，为后续诊断序列确认范围；确认两个层级的范围可不同且关联正确。
4. 切换任一序列的扫描方向，确认该序列的范围数值与裁剪框不发生交换或跳变。
5. 返回、刷新和继续当前会话，确认 Topogram 与诊断序列的范围仍分别绑定至正确序列。
6. 检查普通用户页面不存在“进床 / 出床”作为扫描方向的文案。
7. 运行后端单元测试、前端相关测试、`npm.cmd run lint` 和 `npm.cmd run build`。

## 9. 实施前待确认事项

以下事项需要确认后才进入代码实现：

1. WT32 原型中滑轨机架位置的坐标原点、正方向与可用范围。
2. `HFS / FFS / HFP / FFP` 与“头向足 / 足向头”到模拟机架滑轨运动的映射表。
3. 扫描范围是否按本方案挂在每个采集序列上（Topogram 和各诊断序列）；本方案建议“是”。
4. 对历史 `IN / OUT` 模板与会话数据的展示策略：保留为旧数据、标记待确认，还是仅在开发数据中重置。
5. Scout 页面范围边界的最终文案：建议暂用“范围下界 / 范围上界（mm）”，直到设备坐标系名称确认。

## 10. 非目标

- 不接入、控制或验证真实滑轨机架。
- 不生成真实设备运动指令、最终剂量计算或安全批准。
- 不在本次范围内变更非扫描规划模块的既有未提交代码。
