# WT32 整体项目优化计划（2026-07-16）

> 本文是 2026-07-16 时点的优化路线图快照，用于确定先后顺序和阶段门槛，不是已经批准的产品需求或发布日期承诺。WT32 仍是用于产品与 UI 验证的 CT 控制台原型，不代表真实设备控制、诊断结论、治疗建议、最终剂量计算或安全批准。

## 1. 结论先行

WT32 当前不缺功能覆盖，主要问题是功能增长速度已经超过需求收敛、状态治理、自动化验证和模块化速度。因此不建议先继续横向增加高级功能，也不建议先做全局视觉翻新。

推荐顺序如下：

1. **先收敛产品边界和验收基线**：确认哪些能力是真实目标、哪些只是模拟、哪些尚待内部确认。
2. **再稳定核心流程、状态和数据契约**：消除 API、localStorage、IndexedDB 与演示数据之间的隐式竞争，先保证流程正确、可恢复、可追溯。
3. **随后补齐自动化保护并拆分高风险大模块**：测试先保护行为，再做结构调整，避免重构改变扫描语义。
4. **之后统一交互、视觉、本地化和异常反馈**：在稳定流程之上提升 1024×768 触控体验，而不是用界面修饰掩盖状态问题。
5. **再优化影像链路、加载性能和部署质量**：将 Cornerstone/DICOM 重负载与普通控制台路由分离，建立可测量的性能预算。
6. **最后推进高级能力和外部集成**：DOM、剂量、真实呼吸数据、离线重建、设备/服务接入必须以需求批准、接口契约和模拟边界明确为前提。

核心原则是：**先正确、再稳定；先可验证、再重构；先主流程、再高级能力；先明确模拟边界、再讨论真实接入。**

## 2. 本次评估范围

### 2.1 建议改变的内容

- 产品范围、需求证据和阶段优先级的管理方式。
- 患者、协议、扫描会话、扫描执行、图像查看和服务模式之间的状态与数据边界。
- 前后端测试、构建、代码组织、错误恢复、性能、本地化和文档治理。
- 4D、门控、剂量、DOM、对比剂和重建能力进入实施前的验证门槛。

### 2.2 本计划不做的内容

- 不把原型升级表述为临床软件或真实设备控制软件。
- 不批准任何剂量阈值、对比剂规则、扫描参数范围或安全处置策略。
- 不根据页面上出现 `--`、占位按钮或未接数据，就直接判定应新增行为。
- 不替代公司内部设备规范、算法说明、硬件接口文档、医学物理审核或用户研究。
- 不在没有证据时承诺具体发布日期；文中的周期是相对工作量估计，需要按实际人力重新排期。

### 2.3 验证方式

- 每个阶段开始前，从候选需求总账选择对应 ID，完成问题与方案验证卡。
- 每项改动必须有可观察的验收结果；核心流程优先使用自动化行为测试，视觉和真机交互使用固定检查表。
- 每个阶段只有在出口门槛满足后，才进入下一阶段的主体工作。

## 5. 分阶段实施路线

阶段周期按单个稳定小组的相对工程周估算。多个阶段可以做少量准备工作，但不能绕过前置门槛直接大规模实施。

### 阶段 0：建立基线与止损（约 1～2 周）

**目标**：让团队对“现在是什么、要优化什么、什么不能动”形成共同认知，并消除继续开发最容易放大的质量风险。

主要工作：

1. 从 62 条候选需求中先验证与主流程直接相关的 CAND-001、012、017、020、021、030、031、043、044、061。
2. 明确五条黄金流程：常规螺旋、常规轴扫、门控、4D、已完成检查图像查看；为每条流程建立正常、取消、失败、刷新恢复四类验收路径。
3. 记录所有数据来源和状态持久化点，产出“业务对象—权威来源—缓存—失效—恢复”矩阵。
4. 配置前端测试运行器，先覆盖扫描工作流分支、协议模板与会话隔离、剂量/模拟文案边界。
5. 修复当前 25 条 lint warning，优先处理渲染期读取 ref、Hook 依赖和可能产生陈旧闭包的问题。
6. 将后端测试、前端测试、lint、build 纳入统一质量门禁；保留 Cornerstone 构建警告时必须记录原因和后续处理项。
7. 建立版本化问题反馈模板，至少包含版本、场景、复现步骤、预期/实际、截图或视频、设备环境、日志位置和脱敏确认。

**阶段出口门槛**：

- 五条黄金流程的当前行为和预期行为均有书面结论。
- 前端测试命令可在本地稳定运行，最关键的模板/会话隔离和流程分支已有自动化保护。
- 后端测试、前端测试、lint、build 全部通过；没有未解释的 lint warning。
- 团队能够回答任一核心状态由谁创建、由谁持久化、刷新后如何恢复。

### 阶段 1：统一状态、数据与异常恢复（约 2～4 周）

**目标**：先让主流程在刷新、断连、失败和重试情况下仍然一致，再考虑大规模界面或结构优化。

主要工作：

1. 为扫描工作流定义单一状态模型，明确检查、会话、当前序列、采集状态、图像处理状态和最终结果之间的关系。
2. 将协议模板与扫描会话的复制边界写进 API 契约和测试：本次会话修改不得隐式回写模板。
3. 统一 REST 与 WebSocket 事件命名、状态映射、错误码、幂等性和超时策略。
4. 逐页清理“真实 API、静态 mock、本地缓存自动兜底”混用；演示数据必须明确标识，生产路径不得静默显示与患者不匹配的数据。
5. 明确 localStorage 与 Dexie 的职责：只保存恢复所需的标识和快照，不作为不受控的第二业务数据库。
6. 为加载、空数据、断连、超时、失败、重试、取消和降级建立统一状态组件及下一步动作。
7. 对患者身份、当前扫描会话和图像结果关联做端到端校验，优先解决“已完成检查打开固定 mock 图像”的风险。

**阶段出口门槛**：

- 五条黄金流程通过刷新恢复、断连和失败路径验收。
- 任一患者、协议、会话、序列和图像结果都能追溯到明确标识，页面不做静默错配。
- 取消、返回修改、重试当前序列、终止检查的状态和数据保留规则不再混用。
- 4D 与门控使用不同的采集语义、状态分支和后处理路径。

### 阶段 2：测试扩展与架构解耦（约 3～5 周）

**目标**：在行为已被保护的前提下，降低大文件和重复规则带来的修改风险。

主要工作：

1. 按“流程编排、领域状态、API/缓存、可复用交互、纯视图”拆分 `ViewScreen.tsx`、`ProtocolSetupScreen.tsx`、`HelicalScanConfirmScreen.tsx`、`ScoutScanScreen.tsx` 等高风险模块。
2. 将扫描模式共有流程抽成明确的领域服务或 Hook，同时保留常规轴扫、门控与 4D 的差异，不用过度抽象强行合并。
3. 将 `database.py` 中的连接/会话管理、种子协议和初始化职责分离；种子数据采用可校验、可版本化的结构。
4. 将 `i18n.ts` 按患者、协议、扫描、图像、服务模式、通用组件拆分，并建立术语键名规范。
5. 收拢重复的参数校验、单位格式化、错误映射、API 请求和演示标识逻辑。
6. 扩展后端接口测试、前端组件/状态测试和少量黄金流程端到端测试，重点覆盖高风险行为而非追求单一覆盖率数字。
7. 为关键架构决定建立 ADR，例如扫描状态权威来源、缓存策略、图像数据关联和外部服务边界。

**阶段出口门槛**：

- 主要大页面不再同时承担数据获取、流程状态、图像计算和全部视图渲染职责。
- 关键领域规则只有一个权威实现，并有测试覆盖。
- 修改一个扫描模式时，能够通过自动化测试确认没有破坏其他模式。
- 数据库种子、迁移和运行时初始化职责清晰，可独立验证。

### 阶段 3：统一触控体验、视觉与本地化（约 2～4 周）

**目标**：在稳定流程上形成一致、易理解、适合固定控制台的交互系统。

主要工作：

1. 建立最小设计系统：颜色与状态语义、字号、间距、触控热区、按钮层级、表单、弹窗、提示、空态和错误态。
2. 对 1024×768 进行固定视口验收，检查主要操作可达、长文本溢出、软键盘影响、弹窗遮挡和触控误触。
3. 统一患者确认、参数确认、模拟物理按键引导与危险操作的注意力层级，减少重复确认和状态跳变。
4. 所有用户可见文案进入 i18n，完成中文和英文两套布局回归；建立 CT 术语审批清单。
5. 剂量、DOM、对比剂、设备状态和图像质量文案统一使用“预计、参考、模拟、需确认”等限定语。
6. 补齐键盘焦点、对比度、不可仅靠颜色表达状态等基础可访问性规则，兼顾开发调试和非触控场景。
7. 用黄金流程进行小规模任务测试，记录完成率、误操作、返回次数、阻断点和理解偏差。

**阶段出口门槛**：

- 五条黄金流程在中文和英文、1024×768 下通过布局与触控检查。
- 同类状态和操作在不同页面使用同一交互模式。
- 与剂量、安全和真实设备能力相关的文案通过内部术语/边界复核。

### 阶段 4：影像链路、性能与部署质量（约 3～5 周）

**目标**：让普通控制台操作不为影像重依赖付出成本，并使 DICOM/4D 加载可测、可取消、可恢复。

主要工作：

1. 对图像查看、MPR、性能评估等重页面使用路由级动态加载，将 Cornerstone、codec 和专用 worker 从普通控制台首包分离。
2. 为影像加载建立分阶段指标：元数据、首张可见图像、完整序列、4D 相位/床位加载和交互可用时间。
3. 明确 worker、WASM、图像缓存和视口的创建/销毁时机，防止页面切换后的资源泄漏和陈旧任务回写。
4. 支持加载取消、局部重试、失败位置提示、缓存失效和数据来源显示。
5. 对大序列和 4D 数据采用渐进加载、优先级与内存上限策略；性能测试使用经批准的脱敏样本集。
6. 优化构建拆包和静态资源缓存，记录首屏与图像页各自的体积和时间预算。
7. 固化 Windows 本地、目标部署环境和离线/弱网条件下的启动与升级验证步骤。

**阶段出口门槛**：

- 普通患者/协议/扫描路由的初始包不再包含完整影像查看依赖。
- 构建不再产生未解释的大 chunk 或浏览器兼容警告。
- 影像页在约定样本规模下达到经团队批准的首图、完整加载、内存和切换预算。
- 图像加载失败不会白屏，用户始终有返回、重试或取消路径。

### 阶段 5：高级能力与外部集成（按批准需求单独排期）

**目标**：只实现已被证明有价值、能力边界明确、接口可验证的高级功能。

进入条件：

1. 对应候选需求已经由负责人批准，不再处于“待验证”。
2. 公司内部给出正式术语、算法或设备能力边界。
3. 外部接口明确数据来源、单位、采样率、时钟同步、错误码、超时、权限和版本策略。
4. UI 能清楚区分实时数据、离线结果、估算值、参考值和模拟数据。
5. 已定义失败、降级、重试、取消、日志和数据追溯方案。

建议内部顺序：

1. **先做只读、低耦合集成**：真实状态/数据展示、离线结果读取、连接健康检查。
2. **再做可回滚的任务型能力**：离线重建任务、报告生成、数据导入与关联。
3. **之后做需要实时同步的能力**：真实呼吸数据接入、4D 信号质量与分相链路。
4. **最后评估高风险参数和控制相关能力**：DOM、剂量估算/阈值、对比剂联动、设备控制；在 WT32 原型内仍只能以模拟、预计、参考和需确认方式表达，除非项目边界被正式重新定义。

## 6. 跨阶段工作流

以下工作不应被当成最后统一补做，而应贯穿每个阶段：

### 6.1 测试增长顺序

1. 协议模板与扫描会话隔离。
2. 扫描工作流状态与刷新恢复。
3. 4D、门控、常规轴扫的分支隔离。
4. 剂量、DOM、对比剂和模拟边界文案。
5. DICOM/4D 图像与患者/会话关联。
6. 加载、断连、超时、重试和取消。
7. 中英文 1024×768 视觉回归和少量端到端黄金流程。

### 6.2 每项优化的最小交付包

- 对应需求或问题 ID，以及证据来源。
- 当前问题、目标行为和明确不做事项。
- 影响的流程、状态、数据对象和页面。
- 用户可观察的验收标准。
- 自动化测试或固定人工检查项。
- 数据迁移、兼容、回滚与模拟标识说明。
- 更新后的权威文档；重大决定附 ADR。

### 6.3 AI/Codex 协作约束

- 先读取领域边界和对应需求证据，再改扫描、剂量、4D、门控或图像行为。
- 优先让任务保持为可验证的小纵切片，避免一次性重写整个扫描流程或图像查看器。
- AI 生成的参数范围、医学解释、接口假设和“行业惯例”不能直接成为产品事实。
- 每次交付都要运行与风险相称的测试，并报告仍存在的 warning、模拟数据和未确认项。

## 7. 建议的优先级清单

### P0：立即开始

- 验证核心候选需求与 10 类冲突，冻结黄金流程的当前基线。
- 配置前端测试运行器并保护模板/会话、主流程分支和模拟边界。
- 清除 25 条 lint warning，建立统一质量门禁。
- 统一扫描状态、数据权威来源、患者/会话/图像关联。
- 规范取消、重试、断连、加载失败和刷新恢复。
- 禁止未标识的 mock/演示数据静默进入真实患者流程。

### P1：P0 稳定后进行

- 拆分超大页面、`database.py` 和 `i18n.ts`，收拢重复领域规则。
- 建立 1024×768 设计系统、中英文验收和统一错误状态。
- 进行影像路由拆包、资源生命周期和渐进加载优化。
- 明确权限、患者脱敏、审计事件和真机反馈上下文。
- 建立 ADR 与版本化架构/接口说明。

### P2：有批准需求和接口条件后进行

- 真实呼吸系统、4D 信号质量与分相集成。
- 离线重建和外部服务任务化接入。
- 剂量估算/参考阈值、DOM 和对比剂高级联动。
- 更深的服务模式、设备状态和控制相关能力。

## 8. 不建议现在做的事情

- 不先做全量 UI 换肤或动画升级。
- 不在没有前端行为测试时直接重写全部扫描页面。
- 不为消除重复而把常规扫描、门控和 4D 强行合成一个巨型通用流程。
- 不把所有 localStorage/Dexie 一次性删除；先确认恢复与离线职责，再迁移。
- 不以提高代码覆盖率数字替代关键风险行为测试。
- 不把历史 PRD、页面占位或模型生成建议直接转成开发任务。
- 不在剂量来源、DOM 定义、呼吸接口和设备能力未确认时继续深化参数 UI。

## 9. 复盘节奏与计划维护

- 每周复盘 P0/P1 项的完成、阻塞、风险和基线变化，不按“页面完成数”衡量进展。
- 每个阶段结束时记录测试结果、剩余 warning、性能数据、未验证需求和下一阶段进入结论。
- 当产品边界、数据来源或外部接口发生实质变化时，新建一份带日期的计划或 ADR，并引用本文。
- 本文作为历史快照保持不变；实施中的实时状态应进入任务跟踪系统，而不是不断改写本归档文件。
