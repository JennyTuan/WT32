# WT32 阶段 0：状态与数据来源矩阵

> 本文描述当前实现中的数据流与竞争关系，不把现状自动批准为目标架构。后端数据库在本地可能使用 SQLite 兼容路径，在配置环境中使用 PostgreSQL/Alembic；本文统一称“后端数据库”。涉及患者、扫描、剂量、呼吸、设备或影像的数据都不得因本地缓存或静态兜底而被描述成真实结果。

## 1. 读取原则

- **权威来源**：发生冲突时，当前应优先相信的业务记录。
- **缓存/快照**：为页面选择、恢复、性能或演示服务，不得无版本地取代权威来源。
- **瞬时状态**：仅在当前组件生命周期存在；刷新后丢失是当前事实，不代表产品允许丢失。
- **失效**：何时主动删除、重建或拒绝使用旧值。
- **恢复**：刷新、重新进入、断连或解析失败后，当前实现怎样继续。

## 2. 业务对象—权威来源—缓存—失效—恢复矩阵

| 业务对象 | 当前权威来源 | 当前缓存/派生副本 | 当前失效机制 | 当前恢复路径 | 已观察风险或待验证结论 |
| --- | --- | --- | --- | --- | --- |
| 患者主数据 | 后端 `patients` 表及患者 API | 患者列表的 React state；`localStorage.selectedPatient` 保存当前患者摘要 | 选择另一个患者会覆盖摘要；开始新检查会清扫描上下文，但不会清选中患者；未见对摘要的版本校验 | 患者列表重新请求后端；扫描页通常直接读本地摘要，不按患者 ID 重新校验 | 后端患者修改后，本地姓名、性别、年龄可能陈旧；行末“查看影像”入口未保存同等患者上下文 |
| 患者最新检查摘要 | 后端按 `ScanSession.created_at/id` 选取每位患者最新会话，并派生状态、会话 ID、采集类型、名称和完成时间 | 患者列表 React state | 路由 key 改变或点击刷新时重新请求；没有长期浏览器缓存 | 重新进入/刷新患者列表 | “最新创建”不等于“最后完成”；新建 `draft/in_progress` 会话会遮住更早已完成检查，这是当前规则，是否符合业务待验证 |

| 当前选中扫描会话标识 | 后端会话 ID 是业务标识；浏览器 `localStorage.selectedScanSessionId` 决定前端当前对象 | 无额外索引；部分页面还持有 React 会话对象 | 新检查清理、通用取消、查看器结束时删除 | 有 ID 时可按 ID 请求 `/api/scan-sessions/{id}`；无 ID 时返回 `null` | ID 与 `selectedPatient`、工作流计划分别存储，没有原子一致性校验；可能出现患者 A 摘要配会话 B |
| 扫描会话详情和本次参数 | 后端 `scan_sessions` 及 `scan_session_*` 表 | `localStorage.selectedScanSessionDetail` 保存完整详情；多个页面有 React 副本 | 只有部分会话级/结构操作会刷新详情缓存；清会话 ID 时一并删除。单项参数更新、序列执行更新通常不刷新完整详情缓存 | `fetchSelectedScanSession()` 默认优先缓存；传 `preferCache:false` 才强制请求后端 | 详情缓存可能长期落后于单项 PUT 结果；查看器默认优先缓存，可能展示旧状态/参数。缓存没有 schema 版本、时间戳或 ETag |
| 协议模板到扫描会话的复制关系 | 后端创建会话时克隆协议、序列、采集参数、重建、门控和 4D 配置，并保存模板来源 ID | 工作流计划保存 `protocolId/sourceSeriesId/sourceReconIds`；会话实体保存 `template_*` 外键 | 模板后续变更不应自动使既有会话副本失效 | 按会话 ID读取本次快照；必要时用模板来源 ID 追溯 | 隔离原则明确，但需要自动化证明“会话改动不回写模板、模板改动不改既有会话” |

| 序列执行与定位范围状态 | 后端 `ScanSessionSeries.execution_status/failure_reason/range_confirmed` | 会话详情缓存和各页 React state | execution API 更新；定位像重跑或失败会清 `range_confirmed` | 强制请求会话详情 | 单项 execution 更新不刷新完整详情缓存；常规轴扫可留下 `running` 而会话已 `completed`。门控确认页遗漏范围确认的问题已于 2026-07-16 修复并有 helical/axial 对称回归；门控确认与执行现绑定同一患者、会话、目标序列及前置定位像，终态会话禁止重启或再次确认范围 |
| 定位像选择范围/裁剪 | 后端本次 helical/axial 参数中的 `scan_length/fov` 应承担本次参数记录；`range_confirmed` 表示前置条件 | `localStorage.scoutPositioningRange` 保存 start/end；确认页 React crop box；部分修改 180 ms 防抖后写后端 | 开始新检查时清本地范围；防抖计时器卸载时取消；定位像重扫清 `range_confirmed` | 确认页读取本地范围并结合会话参数重建裁剪框 | 本地范围和后端参数是两种表达，没有版本/时间冲突规则；刷新发生在防抖写入前时可能只保留旧后端值或旧本地范围 |
| 定位像/正式扫描的页面执行阶段 | 无统一持久化权威；当前由页面 React state、计时器和动画驱动 | `stage`、进度、床位、暂停、弹窗、重试计数等组件状态 | 页面卸载、刷新或路由切换即失效 | 当前多数执行页回到 `idle`，仅重新读取部分会话/参数 | 后端可能已经 `running/image_ready`，页面却回到可触发状态；存在重复模拟触发和状态倒退风险。若要求恢复，需提升为显式工作流状态 |

## 3. 当前读取优先级（已观察事实）

### 3.1 会话读取

```text
selectedScanSessionId
  → fetchSelectedScanSession()
      → 默认先读 selectedScanSessionDetail
      → 只有缓存不存在/无效或 preferCache=false 时请求后端
```

这意味着“浏览器刷新后能打开页面”不等于“恢复了后端最新状态”。阶段 0 的工程默认应是：流程判断、执行前置条件和检查完成状态使用后端强制读取；完整详情缓存只用于短暂首屏占位，并带版本或失效依据。

### 3.2 协议选择与会话副本

```text
后端协议目录/详情
  → 用户选择计划
  → 后端克隆成 ScanSession + ScanSessionSeries + 参数副本
  → 本次页面修改会话副本
```

Dexie 中的业务快照、`selectedProtocol` 和工作流计划只提供显示/选择上下文，不应覆盖已创建会话。该边界应先用测试锁定，再做缓存重构。

### 3.3 图像查看

```text
选中会话 ID / route state
  → 会话元数据树
  → 按 demo 识别、工程师 manifest 或固定静态路径选择像素数据
  → 失败时仍可能使用静态 fallback
```

当前链路没有一个“scan_session_id → image manifest/study UID → series UID → instance URL”的统一契约。因此只能表述为演示查看，不能声称完成检查与影像已可靠一一对应。

## 4. 已确认的竞争与断裂点

| 优先级 | 竞争/断裂 | 影响 | 阶段 0 处置 |
| --- | --- | --- | --- |
| P0 | 后端会话详情 vs 无版本 localStorage 全量缓存 | 页面可能用旧参数、旧状态和旧序列 | 流程判断强制读取后端；为缓存增加版本/更新时间/显式失效测试 |
| P0 | 后端序列状态 vs React 执行动画状态 | 刷新后可出现后端 `running`、页面 `idle` | 先写刷新回归；定义恢复映射前不做静默重触发 |
| P0 | 会话/患者/工作流计划三个本地键非原子 | 可能把不同患者、会话和协议计划组合在一起 | 加入组合一致性校验和清理测试；页面显示冲突而不是猜测 |
| P0 | 4D route state/mock vs 检查会话 | 刷新或历史查看产生不同结果 | 显式标识 mock；等待 D0-005/D0-006 后建立检查级结果契约 |
| P0 | 会话元数据树 vs 固定静态像素 URL | 用户看到与当前检查无明确关联的图像 | 不再把 fallback 称为本次检查影像；无关联时显示演示或缺失 |
| 已处理 | 门控后端范围前置条件 vs 确认页缺少写入 | 原实现会使正常门控在正式序列启动时被 409 拒绝 | 已补最近前置定位像判定、显示就绪门禁、范围确认写入和 helical/axial 回归；完整 UI 仍待具备 RespiraScope 的环境验证 |
| 已防错 / 已决策待实施 | `cancelled` 会话 vs UI 返回确认后的下一步 | 已阻止 `cancelled + running`、终态会话再次确认/启动及通用更新回流；门控中断序列当前临时映射为 `failed`，返回页面后的产品入口仍不完整 | 按已批准 D0-002 实现四个独立动作及各自状态，不再共用一个处理 |
| P1 | Dexie 快照 marker vs 实际内容 | 内容变化但 marker 不变时缓存不更新 | 使用内容 hash/schema version 或由后端版本号驱动 |
| P1 | 已完成快捷图标 vs 底部查看按钮 | 当前患者上下文写入不同 | 两个入口复用同一选择函数并加测试 |

## 5. 已批准目标下的读取规则

1. 页面只在本地保存 `{patient_id, scan_session_id, workflow_version}` 等恢复最小标识。
2. 进入任何黄金流程页面时，先以 `scan_session_id` 请求后端当前快照；本地缓存只有在版本一致时可用于首屏。
3. 后端返回会话时同时校验患者 ID、协议来源和序列集合；不一致时阻止继续并给出返回患者列表/重新选择入口。
4. 执行状态采用后端可恢复的状态与显式事件；页面动画从状态派生，不反过来成为业务事实。
5. 4D 后处理和影像 manifest 必须以会话/Study/Series 标识关联；缺失时显示“数据未提供/加载失败”，不生成替代患者结果。
6. mock 和静态 demo 使用独立演示模式标识，并在截图、日志和问题反馈中携带该标识。
7. 按已批准 D0-002/D0-004 实现取消、重试、部分结果和完成的显式状态转移；当前临时防错映射不得被当作最终产品语义。

## 6. 矩阵验证方法

对每一行至少记录以下证据：

- 创建该对象的接口或页面。
- 浏览器存储键、后端 ID 和 schema/version（如有）。
- 修改后，后端响应、本地缓存和下一页面分别看到的值。
- 删除/失效动作后，旧值是否还能影响流程。
- 在加载中、写入后、路由后分别刷新页面的恢复结果。
- 后端断开、返回 404/409/500、缓存损坏时的用户可见状态。
- 使用的是后端记录、估算值、静态演示数据还是生成的 mock。

验证结果统一记录到 [五条黄金流程当前基线](WT32_PHASE0_GOLDEN_WORKFLOWS.md) 的对应检查 ID；目标机证据使用 [非本机与真机环境问题反馈模板](WT32_NON_LOCAL_TEST_FEEDBACK_TEMPLATE.md)。
