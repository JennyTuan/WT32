# WT32 阶段 0：五条黄金流程当前基线

> 本文冻结“当前代码怎样运行”，用于后续自动化和人工回归，不批准新的临床或设备工作流。本文所称“扫描、曝光、完成”均指原型中的模拟流程或后端状态；不表示真实设备已执行。D0-001 至 D0-009 已于 2026-07-16 批准，正式目标见 [阶段 0 产品基线](../../baseline/2026-07-16-WT32-阶段0产品基线.md)。

## 1. 证据范围与结论等级

### 已观察事实

- 所有受保护页面路由定义在 `ui-review/src/App.tsx`。
- 当前患者、工作流计划和选中扫描会话分别由 `patientSession.ts`、`scanWorkflowSession.ts`、`scanSession.ts` 管理。
- 后端会话状态为 `draft / in_progress / completed / cancelled`；序列执行状态为 `pending / running / image_ready / failed`。
- 协议选择时创建扫描会话快照；扫描页修改的是会话副本，不应隐式回写协议模板。
- 定位像完成后，后端会把定位像序列标为 `image_ready`；正式序列开始前，后端要求前置定位像同时满足 `image_ready` 和 `range_confirmed=true`。

### 待运行验证

本文路径与状态差异主要来自静态代码审查，尚未在目标机上逐条完成五条流程的正常、取消、失败和刷新验证。2026-07-16 已完成代码级质量门禁，并在本地 UI 运行到 `/scout-scan`；由于当前开发环境的 RespiraScope 健康检查返回 404，后续定位像与正式序列浏览器验证未继续。因此未被实际完整操作覆盖的检查项仍保持“待运行”，不能写成“已通过”。

## 2. 共用入口和定位像阶段

```text
/patients
  → /protocol-select
  → /scout-scan
  → /scan-confirm
  → /scout-execute
  → 按下一正式序列分支
```

### 当前共用行为

1. 在患者列表选择待检查患者后，前端把患者摘要写入 `selectedPatient`。
2. 协议选择页从后端读取协议目录；开始流程时把计划写入 `selectedScanWorkflowPlans`，并从协议模板创建后端扫描会话快照。
3. 会话创建后状态为 `draft`，选中会话 ID 和一份详情缓存写入浏览器本地存储。
4. `/scout-execute` 的模拟触发会调用会话 `start`，再把定位像序列标为 `running`。
5. 定位像资源加载成功后标为 `image_ready`；加载失败或超时后标为 `failed`，页面提供重试。
6. 定位像完成后按正式序列类型进入以下路由：

| 下一序列 | 路由 |
| --- | --- |
| 常规螺旋 | `/helical-confirm` |
| 常规轴扫 | `/sequence-confirm` |
| 门控螺旋 | `/gated-helical-confirm` |
| 门控轴扫 | `/gated-axial-confirm` |
| 4D | `/fourd-confirm` |

## 3. 黄金流程一：常规螺旋

### 当前路径

```text
共用定位像阶段
  → /helical-confirm
  → /helical-execute
  → /image-viewer
  → “结束检查”
  → /patients
```

### 当前状态写入

- `/helical-confirm` 从后端重新读取会话和参数；只有前置定位像 `image_ready` 且显示资源就绪时才能继续。
- 继续前把前置定位像写为 `range_confirmed=true`。
- `/helical-execute` 调用会话 `start`，把螺旋序列写为 `running`。
- 模拟渲染完成后把螺旋序列写为 `image_ready`，随后把会话写为 `completed`，再自动进入查看器。
- 查看器“结束检查”会再次调用 `complete`；后端对已完成会话直接返回，因此当前调用基本幂等，之后清除选中会话缓存。

## 5. 黄金流程三：门控

门控保持前瞻式采集语义，与回顾式 4D 分开。当前包含两条分支：

```text
门控螺旋：共用定位像阶段
  → /gated-helical-confirm
  → /helical-execute?mode=gated_helical&...
  → /image-viewer

门控轴扫：共用定位像阶段
  → /gated-axial-confirm
  → /helical-execute?mode=gated_axial&...
  → /image-viewer
```

### 当前状态写入与关键差异

- 门控确认页读取会话中的默认门控配置，但当前页面编辑主要保存在组件状态和进入执行页的 URL 查询参数中，没有回写门控配置。
- 门控螺旋和门控轴扫复用 `/helical-execute`；完成后分别把目标序列写为 `image_ready`、把会话写为 `completed`。
- **已修复工程缺口**：后端在正式序列写为 `running` 前要求前置定位像 `range_confirmed=true`。门控螺旋和门控轴扫确认页现与常规流程一致：选择目标序列之前最近的定位像，要求其已出图且显示资源就绪，点击继续后写入范围确认，写入失败则不导航。确认与执行会校验同一患者、会话、目标序列和前置定位像，并通过 URL 绑定这三个业务对象的 ID；加载、启动和完成均强制读取后端并复核。前端纯函数测试和后端 helical/axial 对称接口测试已通过；完整浏览器流程仍待具备 RespiraScope 的环境验证。
- 门控超时或屏息中断的当前“终止”处理会先把仍在运行的模拟序列写为 `failed` 并注明“完成前被终止”，再等待 `cancelScanSession` 落库后返回；这是阶段 0 为避免 `cancelled + running` 的临时防错映射。D0-002 已批准将“返回修改、重试当前序列、终止检查、保留部分结果后结束”拆成四个独立动作，因此该临时映射需要在生命周期实施阶段替换为正式动作与状态规则。

## 6. 黄金流程四：4D

```text
共用定位像阶段
  → /fourd-confirm
  → 若 mock 结果包含重扫：/fourd-rescan-select
  → /image-load
  → /phase-filter
  → /image-viewer
  → “结束检查”
  → /patients
```

若生成结果不含重扫范围，则 `/fourd-confirm` 直接进入 `/image-load`。

### 当前状态和数据

- `/fourd-confirm` 的扫描进度、暂停、床位和呼吸波形是 React 瞬时状态。

- 4D 主执行页没有把 4D 序列写为 `running/image_ready`；会话已经在定位像阶段变为 `in_progress`，最终主要依赖查看器“结束检查”写为 `completed`。

- `/fourd-rescan-select` 缺少路由状态时显示无效状态；`/image-load` 和 `/phase-filter` 缺少状态时会重新生成 mock，而不是恢复同一检查。

```text
  → 选中一条记录并点击“查看影像”
  → /image-viewer?（通过 location.state 传 offlineRecon）
  → “结束检查”
  → /patients
```

列表行末的图像图标也可直接进入查看器。底部“查看影像”路径会先保存选中患者；行末图标路径只保存会话 ID，未找到等价的患者上下文写入。

### 当前数据关联

- 患者列表从后端患者接口读取“按创建时间最新的一次扫描会话”，以其状态决定待检查/已完成显示。
- 进入普通已完成检查时保存最新会话 ID，并让查看器读取会话树；若会话读取失败或没有专属影像 URL，查看器会继续使用静态 DICOM 兜底。
- 进入已完成 4D 检查时使用 `generateMockScanResult(9, 10, 165.0)` 生成固定结果。
- 查看器读取会话时默认优先使用本地详情缓存；缓存可能落后于后端。

## 8. 第一批自动化保护建议

以下顺序只保护已观察行为和明确项目边界，不提前批准 D0 决策：

1. `protocol_template_edits_do_not_change_scan_session` 与 `scan_session_edits_do_not_change_protocol_template`。
2. `regular_helical_requires_ready_and_confirmed_topogram_before_running`。
3. `regular_helical_marks_series_ready_and_session_completed`。
4. `regular_axial_currently_enters_viewer_with_running_series`，先用回归测试显式记录现状，再按已批准 D0-003 改为正式模拟执行与合法序列终态。
5. `gating_does_not_enter_4d_post_processing` 与 `four_d_does_enter_phase_post_processing`。
6. `gating_confirmation_confirms_topogram_range_before_series_start`；当前预期会暴露缺口，修复前不得误报为通过。
7. `refresh_rehydrates_from_session_id_instead_of_stale_detail_cache`。
8. `completed_exam_without_linked_images_does_not_silently_show_unrelated_static_data`；按已批准 D0-006 将风险检测升级为强制验收。

10. 对剂量、呼吸和设备状态文案增加“预计/参考/模拟/需确认”边界测试。

## 9. 完成定义

每条检查项只有同时满足以下条件才能从“待运行”改为“通过”：

- 记录实际构建版本、环境、浏览器、1024×768 显示和测试数据标识。
- 记录页面路径、后端会话状态、每个相关序列状态和错误信息。
- 正常、取消、失败、刷新四类至少各有一个可重复结果。
- 不使用真实患者信息；静态或 mock 数据必须在结果中明确标识。
- 若实际行为与本文不同，先更新“已观察事实”；与已批准产品基线冲突时修正实现或发起新的明确变更决策。
