# WT32 候选产品需求总账（第一版）

> 本文档位于 `working`，只用于收集和逐条验证候选需求，不是产品基线，不代表其中任何问题或方案已经成立。

## 1. 使用规则

- 先验证问题，再验证解决方案。
- 当前实现、历史 PRD、测试用例、聊天意见和竞品调研都只是证据来源，不自动等于真实需求。
- 聊天内容按“利益相关方陈述”处理；无法确认的事实标记为“待内部确认”。
- AI 不得补全缺失事实。没有可靠证据时保持“信息不足”。
- 只有 JennyTuan 明确批准的需求与方案才能进入 `docs/baseline/`。
- 每次验证一条稳定编号；不因排序变化重新编号。

## 4. 已识别的冲突与待内部确认主题

这些不是结论，而是后续验证时必须优先澄清的问题：

1. **原型与真机边界**：项目声明不控制真实设备，但聊天出现“部署在真机”和真实呼吸系统接入；需明确原型运行环境与真实控制责任边界。
2. **DOM 定义冲突**：现有资料分别把 DOM 描述为 XYZ 电流调制、器官剂量保护或简单开关；需取得公司内部正式定义。
3. **4D 与门控术语**：资料已倾向“4D 回顾式、门控前瞻式”，但需确认公司产品正式命名和算法范围。
4. **剂量数据来源**：预计剂量、参考阈值、扫描后剂量和定位像剂量的来源与时点尚未统一。
5. **外部呼吸系统**：数据接口、单位、采样率、同步、断连和质量判据缺少公司内部确认。
6. **增强扫描范围**：已有数据对象，但是否属于本阶段真实产品目标尚不明确。
7. **控制台阅片深度**：需要确认它是扫描质量快速确认，还是承担更完整的诊断阅片功能。
8. **协议治理层级**：出厂、机构、科室、用户自定义协议的真实层级和权限尚不明确。
9. **取消、重试和部分数据**：各扫描模式下保留数据、剂量记录和审计语义尚未确认。
10. **服务模式真实性**：各服务页面哪些连接真实状态、哪些只用于产品演示尚未标注。
